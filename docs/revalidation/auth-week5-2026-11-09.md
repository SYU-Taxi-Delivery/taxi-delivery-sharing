## 3. 보완 내용

- 학교 이메일: 공백 제거·소문자 변환 후 도메인이 정확히 일치해야 함. 기본 허용 `syuin.ac.kr`, `syu.ac.kr` (`app.auth.school-email.allowed-domains`로 변경 가능)
- 인증 코드: SecureRandom 6자리, 5분 유효, 5회 틀리면 폐기, 60초 안에 재요청하면 429, 메일 발송 실패 시 코드 폐기 후 503, 인증 완료 상태는 30분 유효·한 번만 사용. 가입용과 비밀번호 재설정용 코드는 서로 쓸 수 없음
- 가입: 비밀번호 8~64자이면서 72바이트 이하(BCrypt 한계). 인증 상태를 원자적으로 가져가 같은 인증으로 동시에 가입해도 1건만 성공. 실패하면 트랜잭션 전체 롤백 후 인증 상태 복구. 동시 가입으로 UNIQUE 충돌이 나면 409 `DUPLICATE_ACCOUNT`
- 로그인: Clock 기반 시각, 잠금 시간이 끝나면 실패 횟수를 0부터 다시 셈, 성공 시 `last_login_at` 기록, 이메일 로그인은 대소문자 구분 없음
- 비밀번호 재설정(신규): `POST /api/auth/password-reset/send-code` `{schoolEmail}`는 가입 여부와 상관없이 같은 200 응답(없는 계정·비활성 계정은 메일 미발송). `POST /api/auth/password-reset/confirm` `{schoolEmail, code, newPassword}`는 성공 시 새 비밀번호 저장, `password_updated_at` 갱신, 실패 횟수와 잠금 해제
- 오류 응답: 사용자/인증 API의 오류를 모집글 API와 같은 JSON 형식(`error.code`, `meta.requestId`)으로 반환 (`AuthExceptionHandler`)
- 권한: `/api/admin/**`는 ADMIN만 접근 (학생 403 `FORBIDDEN_OPERATION`, 비로그인 401)
- `LocalCredential.passwordUpdatedAt`: Hibernate 7에서 `@CreationTimestamp` 컬럼은 UPDATE에서 빠져 재설정 시각이 저장되지 않아 `@PrePersist`로 변경 (스키마 변화 없음)

DB 스키마(V1/V2)와 기존 SQL은 바꾸지 않았다. 새 마이그레이션도 없다.

## 5. 남은 확인 사항

- 실제 팀 사용자 DB의 DDL·복제본 리허설: 자료가 없어 이번에도 수행하지 않음 (모의 DB만 검증)
- 기존 데이터에 대문자가 섞인 `school_email`이 있으면 새 로그인/가입은 소문자로 조회하므로 적용 전에 확인 필요. 조사 SQL: `SELECT COUNT(*) FROM users WHERE school_email <> LOWER(school_email);` (MySQL 기본 콜레이션 utf8mb4_0900_ai_ci는 비교가 대소문자를 구분하지 않아 조회는 되지만, 다른 콜레이션이면 문제가 됨)
- 학생 웹메일 도메인: PR #17 설명의 `@syuin.ac.kr`과 기존 `@syu.ac.kr`을 함께 허용함. 교직원/관리자 도메인 정책은 팀 확인 필요
- 인증 코드 저장소는 서버 메모리라 서버를 여러 대 띄우거나 재시작하면 코드가 공유·유지되지 않음 (Redis/DB 테이블 필요)
- 회원가입 시 USER_AUTH.provider는 기존 값 `SCHOOL_SSO`를 유지함. 실제 SSO는 없으므로 이름 정리는 팀 결정 필요(SSO는 도입하지 않음)
- 세션의 역할은 로그인 시점 값이라 로그인 중 역할이 바뀌면 다시 로그인해야 반영됨
- 비밀번호 재설정 후 기존 로그인 세션을 끊는 기능은 없음
- 실제 SMTP 발송, GitHub CI 결과는 이 환경에서 확인하지 않음
- (인증 범위 밖) MySQL 8.4에서 `ParticipationMySqlIT`의 `TXN_databaseForeignKeyAndStateCheckRejectInvalidDirectWrites`, `TXN_databaseFailureAfterBothTablesWereFlushedRollsBackBoth`(join·cancel·cancelRecruitment·remove 4건), `TXN_failedRejoinRestoresCancelledRecordAndOpenPost` 총 6건이 `main`에서도 실패한다. MySQL의 CHECK 제약 위반(오류 3819)이 Spring에서 `DataIntegrityViolationException`이 아닌 `UncategorizedSQLException`으로 분류되기 때문이다. 기존 MariaDB 결과로는 드러나지 않았던 문제이며 모집글·참여 담당 범위라 이번 PR에서 수정하지 않았다
